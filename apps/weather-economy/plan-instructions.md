## 만들 것 (사용자와 합의된 내용)
경제 블로그 "Financial Diary"(financialdiary.co.kr)에 매일 다시 들를 이유를 만드는 기능.
**날씨를 생활경제 지표와 엮어서 보여준다.** 단순 기온·강수 예보가 아니라:
- 폭염·장마·가뭄 예보 → 배추·무·사과·양파 등 농산물 **실제 시세 변동**과 함께 보여주기 (애그플레이션 관점)
- 한파 예보 → 난방비·에너지 물가와 연결
- 사주·운세는 **넣지 않는다** (애드센스·구글 YMYL 신뢰도 우려로 사용자가 제외 결정)

### 데이터 출처 (사용자가 키를 신청 중)
- 기상청 단기예보 API (공공데이터포털 data.go.kr, `VilageFcstInfoService_2.0` 계열). 필요하면 중기예보도 검토.
- KAMIS 농산물 가격 API (aT 농산물유통정보). **키 발급처가 data.go.kr인지 kamis.or.kr 자체인지, 필요한 값(cert_key, cert_id 등)이 무엇인지 조사해서 계획서에 분명히 적어라** — 사용자가 이걸 보고 키를 받는다.
- 에너지(오피넷 유가 등)는 3차 이후 선택 사항으로만 언급. 이번 범위에 넣지 마라.

### 반드시 지킬 원칙
- 브라우저는 외부 API를 직접 부르지 않는다. API 키는 GitHub Secrets에만 둔다. (환전 계산기와 동일)
- 수집이 실패해도 배포·블로그는 멈추면 안 된다(`continue-on-error`). 앱은 "데이터를 불러오지 못했어요"를 보여주고 멈추지 않는다.
- 현재 배포 일정은 평일 11:30/15:30 KST뿐이다. 날씨는 매일 필요하므로 **주말 포함 일정**과 시각을 제안하되, 환전 수집과 충돌하지 않게 설계하라. 기상청 발표 시각, KAMIS 갱신 시각을 근거로 들어라.
- 날씨→경제 해설 문구는 **규칙 기반 템플릿**(예: 최고기온 33℃ 이상 = 폭염)으로 만든다. 단정하지 말고("오를 수 있어요", "과거에는 ~한 경우가 많았어요") 실제 시세 숫자를 함께 보여준다.
- **투자 권유 금지**: 개별 종목·주식 추천, "사세요/파세요" 문구 금지. 생활 물가·장보기 관점으로만.
- 매일 자동으로 블로그 글을 찍어내지 않는다(저품질 대량 콘텐츠 위험). 이번 범위는 **앱 1개**다.

### 화면 위치 — 두 안을 비교해 추천하라
- A안: `apps/weather-economy/` 앱 페이지 + 기존 "무료 계산기" 아이콘 줄에 등록 (CLAUDE.md 규칙 그대로)
- B안: A안 + 블로그 메인 화면 위쪽에 작은 요약 띠(오늘 날씨 + 시세 한 줄) — 블로그 파일(index.html/build.js)을 건드리므로 CLAUDE.md 예외가 된다는 점, 첫 화면에 글이 보이도록 위쪽을 줄였던 이전 결정(커밋 a5c02aa)과의 충돌을 짚어라.

### 결정이 필요한 것 — 추천안과 함께 제시
- 지역: 서울 하나? 주요 도시 몇 곳 선택? (기상청 격자 좌표 nx, ny 포함)
- 농산물 품목 몇 개, 어떤 기준(소매/도매, 비교 기간: 전주·전월·평년)
- 데이터를 날마다 쌓아둘지(추이 그래프, 2차 "주간 날씨 경제 브리핑" 글의 재료) — 쌓는다면 정적 사이트에서 어디에 어떻게 저장할지

## spec.md에 들어갈 내용
1. 개요, 한 줄 요약, 사용자 흐름 표
2. API 조사 결과 표 (엔드포인트, 파라미터, 응답 필드, 오류 코드, 갱신 시각, 호출 한도, 키 발급 방법) — 출처와 확인됨/미확인 표기
3. **사용자가 키를 받을 때 해야 할 일** (어디서, 어떤 API를 신청, 받은 값을 GitHub Secrets에 어떤 이름으로 넣는지)
4. 화면 구성(모바일 우선, 사용법 안내 문구 포함), A/B안 비교와 추천
5. 날씨→경제 해설 규칙 표 (조건, 연결 품목, 문구 예시)
6. 파일 구조, 수집 스크립트 설계(로그 규칙, 키 노출 금지), JSON 형식 예시
7. 배포 워크플로 변경안
8. 실패 시나리오 표
9. 범위 밖(2차: 주간 브리핑 글, 3차: 에너지·유가)
10. 승인 후 Build/Review 단계에서 확인할 체크리스트
