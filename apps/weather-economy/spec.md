> 상태: **초안 (승인 대기)** · 작성일 2026-10-09 · Plan 서브에이전트
> 대상 폴더: `apps/weather-economy/` (새 앱)
> 같은 구조의 선례: `apps/exchange-fee-calculator/spec-auto-rate.md` — **GitHub Actions가 배포할 때 외부 API를 불러 정적 JSON으로 같이 올리고, 브라우저는 그 JSON만 읽는다.**

## 1. 개요와 사용자 흐름

### 한 줄 요약
매일 배포 때 기상청 단기예보와 KAMIS 농산물 소매가격을 받아 `data.json` 하나로 올리고, 앱은 "앞으로 3일 날씨 → 장바구니 품목 시세가 어떻게 움직였는지"를 규칙 기반 해설과 실제 숫자로 보여준다.

### 왜 만드나
- 경제 블로그 "Financial Diary"에 **매일 다시 들를 이유**를 만든다. 날씨는 매일 바뀌고, 농산물 시세는 평일마다 바뀐다.
- 단순 날씨 앱이 아니라 **"폭염·장마·한파가 내 장바구니에 어떤 영향을 줄 수 있나"**(애그플레이션 관점)를 보여준다.
- 사주·운세는 넣지 않는다(사용자 결정). 투자 권유(종목·"사세요/파세요")도 하지 않는다. 생활 물가·장보기 관점만.

### 사용자 흐름

| 단계 | 화면에서 일어나는 일 |
|---|---|
| 1. 페이지 열기 | 제목, 사용법 안내, 빈 카드 자리(뼈대)가 바로 보인다. `data.json`을 읽는 동안 "불러오는 중…" |
| 2. 0.1초쯤 뒤 | **오늘의 날씨 경제 한 줄**(예: "주요 도시 낮 최고 34℃ — 잎채소 값이 오를 수 있는 날씨예요")과 3일 날씨 카드가 채워진다 |
| 3. 해설 카드 | 조건에 걸린 규칙마다 카드 1장: 날씨 근거(숫자) + 연결 품목의 **실제 소매가격과 1주 전·1개월 전·평년 대비** |
| 4. 도시 바꾸기 | 서울/부산/대구/광주/대전 버튼을 누르면 날씨 카드만 그 도시로 바뀐다(시세는 전국 평균이라 그대로). 선택은 브라우저에 기억 |
| 5. 품목 표 | 아래쪽에 장바구니 6품목 표(오늘 가격, 1주 전 대비 ▲▼ %, 평년 대비 %) |
| 6. 출처·기준 시각 | 맨 아래 "기상청 단기예보(10월 9일 05시 발표) · KAMIS 소매가격(10월 8일 조사)" |
| 걸린 규칙 없음 | "오늘은 장바구니에 큰 영향을 줄 만한 날씨 신호가 없어요" + 품목 표는 그대로 |
| 실패 시 | `data.json`이 없거나 깨졌으면 **"데이터를 불러오지 못했어요. 잠시 후 다시 들러 주세요."** + 사용법·출처 링크만. 앱은 멈추지 않는다. 날씨만/시세만 있으면 있는 쪽만 보여준다 |

## 2. API 조사 결과

> 조사 방법: 웹 검색 + 공식 페이지 열람(WebFetch). **kamis.or.kr의 Open-API 상세 명세 페이지와 data.go.kr 상세 페이지는 이 환경에서 직접 열렸다.** 실제 호출(키 필요)은 하지 않았다.
> "확인됨" = 공식 페이지에서 직접 확인 또는 서로 다른 출처 2곳 이상 일치. "미확인" = 출처 1곳·제3자 자료·추측. 미확인은 구현 후 첫 Actions 로그로 확인한다(환전 계산기 때와 같은 방법).

### 2-2. KAMIS 농산물 가격 (aT 한국농수산식품유통공사)

**키 발급처가 두 곳이다. 둘은 서로 다른 API다.**

| 구분 | ① KAMIS 자체 Open-API (**추천**) | ② data.go.kr "지역별 품목별 도,소매 가격정보 조회" |
|---|---|---|
| 신청 | kamis.or.kr → 고객센터 → Open-API → **Open-API 이용신청** (`/customer/reference/openapi_write.do`) | data.go.kr 15156062 → **활용신청** |
| 받는 값 | **`p_cert_key`(인증 key)** + **`p_cert_id`(요청자 ID)** 두 개 | data.go.kr **일반 인증키** 하나 (기상청 키와 같은 키) |
| 승인 | 신청 후 키 발급. 제3자 자료는 "1영업일 승인"이라고 함 | 자동승인 |
| 장점 | `dailyPriceByCategoryList` 한 번에 **당일·1일 전·1주 전·2주 전·1개월 전·1년 전·평년 가격**이 같이 옴 → 비교가 공짜 | 키 하나로 끝. 기상청과 같은 포털 |
| 단점 | 키·ID 두 개를 관리. 응답 예시가 공식 페이지에 없음 | 응답에 **비교 가격이 없음**(조사일 최저·평균·최고만) → 1주 전·평년을 보려면 날짜별로 여러 번 불러야 하고 평년값은 없음. 2025-12 신설이라 사례가 적음 |
| 상태 | 명세 **확인됨**(kamis.or.kr 상세 페이지) | 페이지 **확인됨**, 상세 명세는 첨부 zip이라 **미확인** |

> 참고: `periodProductList`(신·일별 품목별 가격, **최근 1년**까지 기간 조회)도 확인했다(kamis.or.kr boardno=2, 파라미터 `p_startday, p_endday, p_itemcode, p_kindcode, p_productrankcode, p_countrycode` 등). 이번 버전에서는 안 쓰지만, **시세 기록이 끊겨도 1년치는 나중에 다시 채울 수 있다**는 근거가 된다(5장 저장 방식).

## 3. 사용자가 키를 받을 때 해야 할 일

> 화면 메뉴 이름은 2026-10 기준 공식 페이지 링크를 따랐다. 신청서 입력 항목은 이 환경에서 볼 수 없어 **미확인**이다. 비슷한 이름을 찾으면 된다.
> 키는 **비밀번호처럼** 다룬다. 블로그 글, 코드, 커밋, 채팅에 붙여 넣지 않는다.

### 3-1. 기상청 단기예보 키 (data.go.kr, 약 5분, 자동승인)
1. `https://www.data.go.kr` 로그인(없으면 회원가입).
2. 검색창에 **"기상청_단기예보 조회서비스"** → 결과에서 **오픈API** 탭의 그 항목(번호 15084084)을 연다. 주소: `https://www.data.go.kr/data/15084084/openapi.do`
3. **활용신청** → 활용 목적(예: "개인 블로그 날씨·생활물가 대시보드") 적고 신청. 자동승인이다.
4. **마이페이지 → 데이터 활용 → Open API → 활용신청 현황**에서 승인 확인. **일반 인증키(Decoding)** 를 복사한다. (Encoding 말고 **Decoding**)
5. 참고: 승인 직후 1시간 정도는 "SERVICE_KEY_IS_NOT_REGISTERED" 오류가 날 수 있다고 알려져 있다(**미확인**). 다음 날 다시 확인하면 된다.

### 3-2. KAMIS 키 (kamis.or.kr, 승인까지 1영업일 안팎 — 미확인)
1. `https://www.kamis.or.kr` 회원가입·로그인(카카오·네이버·구글 로그인 가능).
2. **고객센터 → Open-API → Open-API 이용신청**: `https://www.kamis.or.kr/customer/reference/openapi_write.do`
3. 신청서를 작성한다(이용 목적: "개인 블로그 장바구니 물가 대시보드, 하루 20회 이하 호출").
4. 발급되면 두 값을 확인해 적어 둔다.
   - **인증키** → `p_cert_key` 자리
   - **요청자 ID** → `p_cert_id` 자리. 신청 시 쓴 **아이디**(KAMIS 회원 ID 또는 신청 때 정한 ID)일 것으로 보인다 — **미확인**. 발급 화면이나 메일에 "ID"로 따로 나오면 그 값을 쓴다.
5. 문의: KAMIS Open-API 담당 061-930-9971 (공식 페이지 표기).
- 대안: KAMIS 승인이 늦거나 막히면 data.go.kr의 "한국농수산식품유통공사_지역별 품목별 도,소매 가격정보 조회"(15156062)를 활용신청하면 3-1의 같은 키로 쓸 수 있다. 다만 **평년·1개월 전 비교가 없어** 화면이 약해진다(2-2 표). 이 경우 계획 일부를 다시 승인받는다.

### 3-3. GitHub Secrets 등록 (약 3분)
`https://github.com/micky923-hub/my-blog` → **Settings → Secrets and variables → Actions → New repository secret** 를 세 번 반복:

| Name (대소문자·밑줄 정확히) | Secret 값 |
|---|---|
| `KMA_SERVICE_KEY` | 3-1의 data.go.kr **일반 인증키(Decoding)** |
| `KAMIS_CERT_KEY` | 3-2의 인증키 |
| `KAMIS_CERT_ID` | 3-2의 요청자 ID |

목록에 이름만 보이고 값은 다시 볼 수 없는 것이 정상이다. 키 하나만 먼저 넣어도 된다(그 데이터만 나온다).

### 3-4. 처음 한 번 수동 실행 (구현이 main에 머지된 뒤)
1. **Actions → Deploy to GitHub Pages → Run workflow**.
2. **Fetch weather & produce prices** 단계를 펼쳐 `[weather] 저장`, `[prices] 저장` 줄을 확인. `키 없음`이면 Secret 이름 철자, `resultCode=30`이면 승인 대기·키 종류(Decoding인지), `error_code=900`이면 KAMIS 키/ID를 확인.
3. `https://financialdiary.co.kr/apps/weather-economy/data.json` 과 앱 화면을 확인.

### 4-2. 화면 위치 — A안 vs B안

| 기준 | **A안**: 앱 페이지 + "무료 계산기" 아이콘 줄 등록 | **B안**: A안 + 블로그 메인 위쪽 요약 띠 |
|---|---|---|
| CLAUDE.md 규칙 | 그대로 지킴(`apps/weather-economy/` + `apps.json` 한 줄 추가, Embed 단계의 정해진 방식) | **예외 필요**: `build.js`(메인 HTML 생성) + `css/style.css`(띠 스타일) 수정. `index.html`은 `build.js`가 만들므로 실제로는 build.js를 고쳐야 함 |
| 첫 화면 | 영향 없음 | 커밋 a5c02aa(2026-10-08)에서 **첫 글이 바로 보이도록 위쪽을 줄인 결정**과 충돌. 띠 한 줄(약 40~60px)이라도 휴대폰에서 첫 글이 다시 내려간다 |
| 데이터 실패 시 | 앱 안에서만 "불러오지 못했어요" | 메인에 빈 띠/오류 띠가 생길 위험 → 숨김 처리 로직 필요 |
| 메인 성능 | 영향 없음 | 메인이 `data.json`을 추가로 fetch(작지만 요청 1개 증가) |
| 재방문 유도 | 아이콘 줄의 한 칸 | 더 강함(매일 바뀌는 한 줄이 첫 화면에) |
| 애드센스/품질 | 영향 없음 | 영향 작음. 단 메인 첫 화면이 "날씨 앱"처럼 보이면 블로그 주제가 흐려질 수 있음 |

**추천: A안으로 시작.** 규칙 예외가 없고 a5c02aa 결정과 충돌하지 않는다. 앱이 2~4주 안정적으로 돌고 나서(수집 성공률 확인 후) B안을 **별도 계획**으로 다시 판단하자. 그때는 띠 대신 아이콘 줄의 이 앱 타일에 "34℃ · 배추▲" 같은 **작은 배지**를 붙이는 C안(첫 화면 높이 변화 없음, 다만 build.js 수정 필요)도 같이 비교할 것을 제안한다.

- 참고: 아이콘 줄 제목이 "무료 계산기"인데 이 앱은 계산기가 아니다. 제목을 바꾸려면 `build.js` 수정이라 **이번엔 그대로 둔다.** `apps.json`의 `shortTitle`은 **"날씨 장바구니"**, 아이콘은 `apps/weather-economy/icon.svg`(다른 앱과 같은 64×64 형식, 밝은 색감).

## 5. 날씨 → 장바구니 해설 규칙

### 5-1. 품목 (추천 6개, 소매, 전국 평균)

| 품목 | 부류 | 고른 이유 | 비고 |
|---|---|---|---|
| 배추 | 200 채소류 | 폭염·장마·한파 모두에 민감, 김장 물가 대표 | |
| 무 | 200 | 배추와 함께 김장 물가 | |
| 상추 | 200 | 잎채소 — 폭염·장마에 가장 빨리 반응 | |
| 대파(파) | 200 | 한파·장마에 민감, 장바구니 체감 큼 | KAMIS 품목명 "파"(미확인) |
| 양파 | 200 | 저장성 채소 — 날씨 영향이 느림(대조군 역할) | |
| 사과 | 400 과일류 | 폭염·가뭄(일소·착색), 명절 물가 | |

- **소매(01)** 를 쓴다: 장보기 관점. 도매는 2차.
- 지역: `p_country_code` **생략(전체 지역)**. 생략 시 전국 평균 한 줄이 오는지, 지역별 여러 줄이 오는지는 **미확인** → 여러 줄이면 "전국 평균"이 아닌 **서울(1101)** 로 바꾸고 화면 문구도 "서울 소매가격"으로 바꾼다(Build에서 첫 응답 보고 결정, Review에서 확인).
- 품종·등급: 품목마다 KAMIS 응답 중 **첫 번째 "상품" 등급** 1줄을 고정해서 쓴다(Build 단계에서 실제 `kind_name`/`rank`로 표 확정해 이 문서 부록에 적는다).
- 비교 기간: **1주 전(dpr3), 1개월 전(dpr5), 평년(dpr7)**. 1일 전은 변동이 작고, 1년 전은 평년과 겹쳐 뺀다. 1개월 전·평년은 5일 이동평균이라고 화면 주석에 적는다.
- 호출: 채소류(200) 1회 + 과일류(400) 1회 = **실행당 2회**(데이터 없으면 날짜를 거슬러 최대 7회씩).

### 5-2. 날씨 판정 기준 (단기예보 기준, 오늘~모레 3일)
"주요 도시" = 서울·부산·대구·광주·대전 5곳. 산지 날씨가 아니라 **도시 예보**라는 한계를 화면 주석에 적는다.

| 신호 | 조건 (규칙 엔진이 계산) | 근거 |
|---|---|---|
| 폭염 | 3일 중 하루라도 5개 도시 중 **3곳 이상** `TMX ≥ 33℃` | 기상청 폭염주의보 기준(일 최고 33℃ 이상 2일 지속 예상)을 단순화 |
| 극심한 폭염 | 3곳 이상 `TMX ≥ 35℃` | 폭염경보 기준(35℃) 단순화 |
| 장마·집중호우 | 3곳 이상이 3일 중 **2일 이상** 일 최대 `POP ≥ 60%` **또는** 하루 예상 강수 합 ≥ 30mm | 자체 기준(근거: 강수확률 60% 이상이 '비 예보' 표현 기준으로 흔히 쓰임 — 미확인) |
| 한파 | 3곳 이상 `TMN ≤ -12℃` 또는 서울 `TMN ≤ -10℃` | 한파주의보(아침 최저 -12℃ 이하 2일 이상 등) 단순화 |
| 가뭄(건조) | **누적 기록 14일 이상 있을 때만**: 최근 14일 5개 도시 예보 강수 합이 거의 0 + 앞으로 3일 `POP < 30%` | 단기예보만으론 가뭄 판단이 어려워 **기록이 쌓인 뒤에만** 켬. 기록 부족하면 규칙 자체를 숨김 |
| 첫눈·대설 | 3곳 이상 `SNO` 1cm 이상 | 자체 기준 |

(기상청 특보 기준 수치는 일반에 알려진 값으로, 이 환경에서 기상청 원문을 열람하지는 못함 → **미확인 표기**하고 화면엔 "기상청 특보 기준과 비슷한 수준"이라고만 쓴다.)

| 한파 | 배추, 무, 대파 | "아침 최저 **-13℃** 예보예요. 한파 때는 노지 채소 수확이 늦어져 **값이 오르는 경우가 있었어요.** 난방비도 함께 늘 수 있는 시기예요." + 시세 (난방비 수치는 3차) |
| 가뭄(건조) | 무, 배추, 양파 | "2주 넘게 비 소식이 거의 없어요. 가뭄이 길어지면 뿌리채소 생육에 영향을 줄 수 있어요." + 시세 |
| 첫눈·대설 | 배추, 대파 | "눈 소식이 있어요. 길이 막히면 산지 출하가 늦어져 일시적으로 값이 오를 수 있어요." + 시세 |
| 시세 단독 | (날씨 신호와 무관) | 평년 대비 **±30% 이상**인 품목이 있으면 표에서 강조만 하고 "평년보다 많이 비싸요/싸요"를 표시. 원인을 날씨로 단정하지 않는다 |

**문구 원칙(Review에서 grep으로 검사)**
- 쓰는 말: "오를 수 있어요", "~한 경우가 많았어요", "참고하세요".
- 쓰지 않는 말: "오릅니다", "확실", "반드시", "지금 사세요/파세요", "투자", "종목", "매수", "매도", 특정 기업·ETF 이름.
- 시세가 날씨 방향과 **반대**(예: 폭염인데 상추 ▼)면 그대로 보여준다: "지금은 1주 전보다 낮아요. 날씨 영향은 보통 며칠~몇 주 뒤에 나타나요."
- 가격이 없으면 그 품목 줄은 "가격 정보 없음".
- 해설 카드 최대 3장(우선순위: 극심한 폭염 > 한파 > 장마 > 폭염 > 대설 > 가뭄).

### 6-2. 수집 스크립트 `fetch-weather-economy.js`

| 규칙 | 내용 |
|---|---|
| 실행 | `node fetch-weather-economy.js --out <경로> [--weather-fixture <파일>] [--prices-fixture <파일>] [--fallback-url <URL\|경로>] [--now 2026-10-09T06:20+09:00]` |
| 키 | `process.env.KMA_SERVICE_KEY`, `KAMIS_CERT_KEY`, `KAMIS_CERT_ID`만 읽는다. 없으면 그 부분만 건너뛰고 "키 없음" 로그 |
| 로그 접두사 | `[weather]`, `[prices]`, `[history]`, `[out]` |
| **로그에 키 금지** | 요청 URL을 **절대 출력하지 않는다.** 출력 전 `mask()`: 세 키 원문·`encodeURIComponent` 형태를 `***`로, `serviceKey=`/`p_cert_key=`/`p_cert_id=` 뒤 값을 `***`로, `apis.data.go.kr`·`kamis.or.kr` 주소는 `[API 주소 생략]`으로. 환전 스크립트의 `mask()`와 같은 방식 |
| 날씨 회차 고르기 | 지금(KST) 기준 가장 최근 발표 시각 중 **발표+60분이 지난 회차**. 응답이 NODATA(03)/빈 items면 직전 회차로, **최대 3회차** |
| 날씨 호출 | 도시 5곳 × 1회(`numOfRows=1000`, `totalCount`가 더 크면 2쪽까지). 오늘~모레 3일만 남김 |
| 날씨 요약 | 도시·날짜별 `tmx, tmn`(없으면 `TMP` 최고·최저로 대신, `tmxFrom:"TMP"` 표시), `popMax`, `pcpSum`(문자열 범주는 하한값 — 예 "1mm 미만"=0.5, "30.0~50.0mm"=30, "50.0mm 이상"=50), `snoSum`, `skyNoon`, `ptyAny` |
| 시세 회차 | `p_regday` = 오늘(KST)부터 하루씩 거슬러 `001 no data`이면 전날, **최대 7일**(연휴 대비). `900`(인증)·`200`(파라미터)은 **즉시 중단** |
| 시세 파싱 | 쉼표 제거 → `^\d+(\.\d+)?$` → 정수(원). 0 이하·1,000,000 초과·숫자 아님 → `null` |
| 시간 제한 | 요청당 10초(`AbortSignal.timeout(10000)`), 요청 사이 0.3초 쉼 |
| TLS | 인증서 검증을 **끄지 않는다**. KAMIS https 실패 시 **http로 자동 전환하지 않는다**(키가 평문 노출). 로그에 `cause.code` 남기고 대비책 |
| 대비책 | 날씨·시세 **각각 따로**: API 실패 시 현재 사이트의 `data.json`을 받아 그 부분만 재사용(`origin:"previous-deploy"`, 원래 기준 시각 유지). 날씨는 **36시간**, 시세는 **10일** 넘게 오래됐으면 재사용하지 않음 |
| 기록 누적 | 6-4 참고 |
| 종료 코드 | **항상 0.** 최상위 `try/catch` + `unhandledRejection` 처리 |
| 순수 함수 export | `pickBaseTime`, `summarizeForecast`, `parsePcp`, `parsePrice`, `pickItems`, `classifyKmaResponse`, `classifyKamisResponse`, `mergeHistory`, `validateDataJson` |

로그 예시(키·URL 없음):
```
[weather] 회차 20261009 0500 → 서울(60,127) resultCode=00, 항목 1,032개
[weather] 서울 10/09 TMX 24 TMN 14 POP 20 PCP 0
[prices] 채소류(200) p_regday 2026-10-09 → error_code=001 → 전날로
[prices] 채소류(200) p_regday 2026-10-08 → 000, 품목 87줄
```

| 필드 | 설명 |
|---|---|
| `version` | 1이 아니면 앱은 전체를 "불러오지 못했어요"로 처리 |
| `weather` / `prices` | **각각 없어도 된다**(`null`). 있는 쪽만 표시 |
| `origin` | `"api"` \| `"previous-deploy"` (디버그용) |
| `days[].tmxFrom` | `"TMX"` \| `"TMP"`(대체 계산) |
| `prices.items[]` | 값이 없으면 `null`. 변화율은 **앱이 계산**(JSON엔 원값만) |

### 6-4. 데이터를 날마다 쌓을까? — 추천: **쌓는다(가볍게)**

| 방법 | 장점 | 단점 |
|---|---|---|
| ⓐ 안 쌓음 | 가장 단순 | 가뭄 규칙 불가, 2차 "주간 브리핑" 재료 없음, 추이 그래프 불가 |
| **ⓑ 이전 배포본 이어붙이기 (추천)** | 환전 계산기의 대비책과 같은 방식. 저장소 커밋 없음, 권한 그대로(`contents: read`) | 한 번이라도 이전 `data.json` 다운로드가 실패한 채 배포되면 **그동안의 기록이 끊길 수 있음** |
| ⓒ 저장소에 매일 커밋 | 기록이 git에 영구 보존 | `contents: write` 필요, 매일 봇 커밋이 글 이력을 묻음, 환전 때 (B)를 거절한 이유와 동일 |
| ⓓ Actions 캐시/아티팩트 | 저장소 깨끗 | 캐시는 7일 미사용 시 삭제·용량 제한, 아티팩트는 보존 기간 제한 → 장기 보관용 아님 |

**ⓑ 보완책**
- 이전 `data.json` 다운로드가 실패하면(배포본이 404가 아닌 네트워크 오류일 때) **1분 뒤 한 번 더** 시도한다. 그래도 실패하면 **오늘 하루치만** 넣고 로그에 `⚠ 기록 끊김`을 크게 남긴다(사용자가 Actions 로그로 앎). `history`를 빼고 배포하면 다음 실행도 빈 기록을 받게 되므로 "빼고 배포"는 해결책이 아니다.
- **시세 기록은 복구 가능**: KAMIS `periodProductList`로 최근 1년치를 나중에 다시 채울 수 있다(2-2 참고). 날씨 기록(예보 요약)은 복구 불가 — 하지만 2차에서 필요한 건 "그 주의 날씨 요약" 정도라 관측자료(기상청 ASOS 일자료 API, 2차에서 조사)로 대신할 수 있다.
- 이번 버전 앱은 기록을 **가뭄 규칙에만** 쓴다. 추이 그래프는 2차.

## 7. 배포 워크플로 변경안 (`.github/workflows/deploy.yml`)

### 7-1. 일정 근거
| 데이터 | 갱신 | 근거·상태 |
|---|---|---|
| 기상청 단기예보 | 02·05·08·11·14·17·20·23시 발표(매일, 주말 포함) | 확인됨 |
| KAMIS 소매가격 | 평일(토·일·공휴일 제외) 조사, **공표 시각 미확인** | 조사일 확인됨 / 시각 미확인 |
| 수출입은행 환율 | 평일 오전 11시 전후 | 환전 계획서(시각 미확인) |

### 7-2. 제안 일정 (GitHub cron은 UTC)

| KST | cron (UTC) | 요일 | 하는 일 | 쓰는 예보 회차 |
|---|---|---|---|---|
| **06:20** | `20 21 * * *` (전날 21:20 UTC) | **매일** | 아침 날씨 갱신(하루의 핵심 실행) | 05시 발표 |
| 11:30 | `30 2 * * 1-5` (기존) | 평일 | 환율 + 날씨 + 시세 | 08시(11시 회차는 60분 미경과) |
| 15:30 | `30 6 * * 1-5` (기존) | 평일 | 환율 + 날씨 + 시세(당일 시세가 올라왔으면 반영) | 14시 |
| **18:20** | `20 9 * * *` | **매일** | 저녁 갱신(내일 날씨, 평일엔 당일 시세 재시도) | 17시 |

- 모든 실행은 **같은 deploy job**에서 환율·날씨·시세를 다 부른다(스크립트 2개가 차례로). 수집이 서로 독립이라 하나가 실패해도 다른 하나는 정상.
- **충돌 방지**: 새 cron은 **:20분**, 기존은 **:30분** → 같은 시각에 겹치지 않는다. 그래도 `concurrency: group: pages, cancel-in-progress: false`가 이미 있어 겹치면 차례로 실행된다.
- 호출량: 날씨 하루 최대 4실행 × 5도시 × (1~3회) ≈ 60회 ≪ 10,000. 시세 실행당 2~14회. 환율은 주말 06:20·18:20 실행에서 빈 배열 → 최대 7회씩 더 부르게 되지만 한도 1,000회에 비해 작다(기존 대비책이 금요일 값 유지).
- 주말 실행은 환율·시세가 변하지 않아도 **같은 값으로 다시 배포**될 뿐 해가 없다.
- 참고: GitHub schedule은 수 분~수십 분 늦을 수 있다(06:20 → 06:40). 05시 발표 기준이라 문제없다. 60일 무활동 시 schedule이 꺼지는 규칙은 매일 cron이 아니라 **저장소 활동** 기준이므로 블로그 글을 꾸준히 올리면 문제없다.
- KAMIS 공표 시각을 모르므로, 첫 2주간 로그의 `p_regday 오늘 → 000/001`을 보고 18:20 실행이 필요한지, 시각을 옮길지 판단한다.

### 7-3. 변경 초안 (추가만, 기존 순서 유지)

```yaml

  schedule:
    - cron: '30 2 * * 1-5'   # 평일 11:30 KST (환율 발표 직후)  ← 기존

    - cron: '20 21 * * *'    # 매일 06:20 KST (기상청 05시 발표 후 날씨)   ← 추가
    - cron: '20 9 * * *'     # 매일 18:20 KST (17시 발표·당일 시세)        ← 추가
  workflow_dispatch:

# permissions(contents: read 그대로), concurrency 그대로
      - run: npm run build

      - name: Fetch exchange rates (Korea Eximbank)      # 기존 그대로
        ...

      - name: Fetch weather & produce prices (KMA, KAMIS)  # 추가
        run: node apps/weather-economy/tools/fetch-weather-economy.js --out dist/apps/weather-economy/data.json
        env:
          KMA_SERVICE_KEY: ${{ secrets.KMA_SERVICE_KEY }}

          KAMIS_CERT_ID: ${{ secrets.KAMIS_CERT_ID }}
        continue-on-error: true

      - uses: actions/configure-pages@v5   # 이하 그대로
```
- 반드시 `npm run build` **뒤**(build.js가 `dist/`를 지우므로).
- 이 예외(블로그 공용 파일 수정)는 환전 계산기 때와 같은 이유: 서버 역할을 하는 곳이 배포 워크플로뿐이다. **사용자 승인 필요.**

## 승인 요청 사항 (요약)
1. **KAMIS는 kamis.or.kr 자체 Open-API(`p_cert_key` + `p_cert_id`)로 신청** — 평년·1개월 전 비교를 한 번에 받기 위해. 기상청은 data.go.kr(자동승인). Secret 이름 `KMA_SERVICE_KEY`, `KAMIS_CERT_KEY`, `KAMIS_CERT_ID`.
2. **A안**(앱 페이지 + 아이콘 줄)으로 시작, 메인 띠(B안)는 2~4주 운영 뒤 별도 판단.
3. **날씨는 5대 도시(서울 기본, 선택 가능), 시세는 소매·전국 평균 6품목**(배추·무·상추·대파·양파·사과), 비교는 1주 전·1개월 전·평년.
4. **매일 06:20·18:20 KST cron 추가**(기존 평일 11:30·15:30 유지, 분을 :20/:30으로 나눠 충돌 방지) + `deploy.yml`에 수집 단계 1개 추가(블로그 공용 파일 예외).
5. **기록은 이전 배포본에 이어붙여 400일 보관**(저장소 커밋 없음). 끊길 위험은 있으나 시세는 KAMIS로 1년치 복구 가능.
